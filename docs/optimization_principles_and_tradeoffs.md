## 二、七大核心优化技术的物理机制深度解析

### 1. PagedAttention：内存虚拟分页消除显存碎片
- **传统缺陷**：原生 Hugging Face 必须为每个请求提前按 `max_model_len` 预分配连续的显存空间。由于无法预知输出长度，导致 **显存内碎片与外碎片高达 60%~80%**，即使显存尚有空余也无法接收新请求。
- **物理机制**：借鉴操作系统虚拟内存分页思想，将 Key 和 Value 张量切分为固定大小的物理块（Block，如 16 个 Token）。请求按需动态申请离散的 Block，由 Block Table 映射为逻辑连续的虚拟上下文。
- **收益**：**显存碎片率降至 <4%**，在相同硬件上能容纳 2 ~ 4 倍的并发序列。

### 2. 模型与 KV 量化 (AWQ / FP8)：破解显存带宽瓶颈 (Memory-Bound)
- **物理机制**：
  - 在 Decode 阶段，生成 1 个 Token 需要将整个模型几十亿参数从 GPU 显存（DRAM）拉取到计算单元（SRAM）。
  - 计算强度（Arithmetic Intensity = FLOPs / Byte）极低，计算核心常处于**“等待数据搬运”的饥饿状态**。
- **优化原理**：
  - 将 16-bit 权重压缩为 4-bit（AWQ）或 8-bit（FP8），**总显存访存字节数直接减少 50% ~ 75%**；
  - 显存带宽读取时间大幅缩短，单字生成耗时（TPOT）呈比例压低，整体 Tokens/sec 吞吐实现 **2x 以上的质变增长**。

### 3. Prefix Caching：Radix Tree 索引消除重复算力开销
- **物理机制**：在多轮对话或大段 System Prompt 场景下，前缀 Token 序列在不同轮次中完全相同。
- **优化原理**：vLLM 将已处理上下文的 KV Block 组织为前缀基数树（Radix Tree）。
- **收益**：后续请求到达时，系统识别出命中前缀，直接通过虚拟地址映射复用已有 KV Cache，**彻底免去前缀几千 Token 的 $O(N^2)$ 自注意力矩阵乘法**，首字延迟（TTFT）降低 **90% 以上（实测 19.7x 加速）**。

### 4. Chunked Prefill：计算密集与带宽密集的时分混合调度
- **物理机制**：长 Prompt 的 Prefill 算力极重（吃满 Tensor Core），流式 Decode 算力极轻但需要极短的周期性响应（吃满显存带宽）。
- **优化原理**：通过 `--max-num-batched-tokens` 将超长 Prefill 切割成若干 Chunk，**在一个调度时间步内既计算一小块 Prefill，又同时捎带完成所有已有并发请求的 1 步 Decode**。
- **收益**：打破了长 Prefill 对 GPU 的完全垄断，彻底消除了流式打字过程中的长时间卡顿停顿。

### 5. 投机解码 (Speculative Decoding)：以验证计算换取串行时间
- **物理机制**：受限于自回归的单字因果依赖，模型每吐 1 个字就必须走一遍完整的深层网络前向传播。
- **优化原理**：
  - 由轻量级机制（如 N-gram 局部查表或 0.5B 草稿小模型）以极低代价一口气预先猜出 $K$ 个后续 Token；
  - 目标大模型在一次前向传播中**并行校验（Parallel Verification）**全部猜词。
- **收益**：用极小算力并行化验证取代了多次串行网络迭代，代码与结构化数据生成速度可提升 **1.4x ~ 2.0x**。

### 6. CUDA Graph：消除 CPU 驱动发射小算子瓶颈
- **物理机制**：在小 Batch 解码时，单个步长内的计算极快（仅数毫秒），但 PyTorch 需要在 CPU 端依次向 GPU 驱动发射数十个小算子（Kernel Launch）。CPU 发射开销往往超过了 GPU 真实计算时间。
- **优化原理**：将固定 Batch Size 的整条推理前向计算链路提前捕获并固化为一张静态图（Static Graph）。
- **收益**：运行时仅需一次 CPU 指令即可触发整张计算图在 GPU 端执行，**彻底消除 CPU 发射瓶颈，小并发单字延迟（TPOT）缩短 30%~50%**。

### 7. PD 分离架构：物理级解耦正交瓶颈
- **物理机制**：Prefill（算力密集）与 Decode（显存带宽密集）共享相同硬件资源时必然存在资源争抢。
- **优化原理**：物理部署 Prefill 专用集群（大算力配置）与 Decode 专用集群（高带宽/多卡低延迟配置），通过跨节点高效通信（PyNccl / RDMA）传递 KV Cache。
- **收益**：Prefill 洪峰无论多猛烈均被阻挡在预填充节点，流式 Decode 节点的单字间隔抖动（Jitter）降低 **60% 以上**。

## 三、吞吐量（Throughput）与尾延迟（P99）的六大核心权衡博弈

在 LLM 推理系统中，**“吞吐量”与“尾延迟”的博弈本质上是并行效率与排队等待的根本冲突**。

```
                    ┌────────────────────────────────────────────────────────┐
                    │               LLM 推理服务的性能平衡天平                │
                    └───────────────────────────┬────────────────────────────┘
                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 ▼                                                             ▼
       【偏向吞吐量 (Throughput)】                                   【偏向尾延迟 (P99 Latency)】
   • 核心诉求: 每秒产出最多的 Token，单位成本最低                 • 核心诉求: 交互丝滑秒开，杜绝打字顿挫卡死
   • 策略特征: 大 Batch、满载显存、长队列合并                    • 策略特征: 小 Batch、保留显存冗余、即到即跑
   • 代价: 排队时间剧增，P99 首字延迟恶化                       • 代价: GPU 算力不饱和，硬件利用率与吞吐降低
```

---

### 博弈 1：批处理大小 (Batching Size) — 显存带宽分摊 vs 队头排队等待

| 侧重方向 | 调度策略 | 物理表现与收益 | 承受的代价 |
| :--- | :--- | :--- | :--- |
| **偏向吞吐** | 设置较大的并发与批处理（如 $c=32$ 或更大） | 每次从显存读取模型权重，可以在同一个 GEMM 中同时服务 32 个请求。**显存带宽读取成本被稀释 32 倍**，Tokens/s 吞吐达到峰值。 | **排队等待（Queue Time）与 P99 尾延迟急剧飙升**。新请求必须在队列等待当前大 Batch，只要有一个长文本在生成，整体迭代步数被迫延长。 |
| **偏向尾延迟**| 严格限制单批次序列数（如 $c=1 \sim 4$） | 请求即到即算，几乎零队列等待，**首字延迟 TTFT 与单字 TPOT 达到硬件极限极值**。 | GPU 显存带宽未被充分榨取，单位 Token 计算成本变高，集群综合吞吐量低下。 |

---

### 博弈 2：分块预填充预算 (`max-num-batched-tokens`) — 算力饱和度 vs 打字机卡顿

| 参数配置 | 适用倾向 | 性能表现特征 | 潜在风险与取舍 |
| :--- | :---: | :--- | :--- |
| **大预算 (如 8192)** | **偏向吞吐** | 允许长 Prompt 一次性整块吞入，Tensor Core 矩阵乘持续处于高饱和运算，**Prefill 吞吐量（Tokens/s）最大**。 | **长 Prefill 占据 GPU 时间过长（单步超 200ms）**，导致并发的流式请求被强制悬挂，流式用户感知到明显的打字顿挫卡顿。 |
| **小预算 (如 2048)** | **偏向尾延迟**| 长 Prefill 被切成微小碎块，流式请求每步只需等待十几毫秒就能吐出下一字，**TPOT P95/P99 维持在平滑的 10ms 级别**。 | 长 Prompt 需要经历多次调度迭代才能计算完毕，增加了调度器开销，**长文本自身的 TTFT 首字响应被推迟**。 |

---

### 博弈 3：显存利用率 (`gpu_memory_utilization`) — 并发容量极限 vs 显存雪崩抢占

| 利用率设定 | 系统行为特征 | 吞吐表现 | 尾延迟稳定性 |
| :--- | :--- | :--- | :--- |
| **极限利用 (0.90 ~ 0.95)** | KV Cache 显存池最大化，能容纳更多并发序列同时驻留显存。 | **极限 QPS 与系统总吞吐极高**，请求无需在前端降速。 | **P99 存在“雪崩式恶化”风险**。显存冗余极小，一旦遇到超长文本生成，显存见顶触发换出（Swap）或抢占重算，**被抢占请求延迟会从几百毫秒暴增至十几秒**。 |
| **稳健利用 (0.80 ~ 0.85)** | 预留充足的显存安全冗余水位（Headroom）。 | 显存池容纳并发量略有缩减，极限吞吐略受制约。 | **绝对杜绝雪崩抢占**。即便遇到突发长文波峰，系统也能平稳消化，**保障 P99/P999 延迟平稳受控**。 |

---

### 博弈 4：投机深度 (`num_speculative_tokens`) — 猜词加速红利 vs 验证回滚惩罚

- **投机步数过长（如猜 $K=6 \sim 8$ 个词）**：
  - **吞吐优势**：在代码生成、固定格式 JSON 任务中，若命中率（Acceptance Rate）高于 80%，单步验证相当于产出 5~7 个 Token，**吐字速度成倍翻番**。
  - **尾延迟代价**：在创意写作或复杂数学推导中，命中率一旦降至 20% 以下，大模型主干网络为校验错词消耗了无效算力，**反而使正常生成延迟变慢 15%~30%，产生极大的延迟抖动**。
- **工程黄金平衡**：一般将投机步数限定在 **$K=3 \sim 4$**，在收益与回滚惩罚之间取得最优平抑。

### 博弈 5：调度策略 (FCFS vs Priority) — 吞吐全局公平 vs VIP 极速插队

- **FCFS（先来先服务）**：
  - 调度器逻辑最简洁，开销最小，流水线平滑，**集群综合吞吐量与公平性最高**；
  - **代价**：当队列被离线批量处理（如数据清洗）占满时，新来的在线 VIP 交互请求产生严重的“队头阻塞（Head-of-Line Blocking）”，**VIP 用户的 TTFT 尾延迟完全失控**。
- **Priority（优先级插队）**：
  - 允许标记了高优先级的请求（`priority=0`）跨越排队队列在下一个 iteration 立即插队执行；
  - **收益**：**VIP 请求首字延迟缩短数十倍**；
  - **代价**：调度器需要动态维护优先级堆栈，若 VIP 请求占比过高可能造成普通离线请求饥饿。

---

### 博弈 6：架构拓扑 (单体混部 vs PD 分离) — 资源装箱密度 vs 严格 SLA 隔离

- **单体架构（Monolithic，偏向资源装箱与成本）**：
  - 在同一颗 GPU 上利用 PagedAttention 和 Chunked Prefill 混部 Prefill 与 Decode，硬件装箱利用率最高，适合单卡/单机私有化轻量部署。
  - **代价**：两类不同物理瓶颈的任务不可避免地存在微秒/毫秒级争抢，极端突发流量下 P99 难以做到物理级隔离。
- **PD 分离架构（Disaggregation，偏向工业级绝对 SLA）**：
  - 将硬件拆分为“Prefill 专用计算池”和“Decode 专用带宽池”，通过高速网络搬运 KV Cache。
  - **收益**：长 Prompt 的计算峰值完全被隔绝在 Prefill 节点，Decode 节点的单字间隔标准差（Jitter）降低 **60% 以上**，达成极致丝滑的在线 SLA。
  - **代价**：增加了节点间网络通信（NCCL/RDMA）延迟与复杂网关路由开销，且当长短文本比例发生偏斜时，容易出现某一方节点的硬件算力空转，**集群整体成本较高**。
